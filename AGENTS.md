# Repository Guidelines

## Project Structure & Module Organization

`src/` contains the library source and public API. The parser pipeline is split into focused modules such as `normalize.ts`, `detect.ts`, `interpret.ts`, `parse.ts`, and `resolve.ts`; shared contracts live in `types.ts`, and package exports are centralized in `src/index.ts`. Scheduling adapters live in `src/scheduling-helpers.ts`.

Keep tests next to the code they cover as `src/*.test.ts`. Use `src/fuzz.test.ts` for property-based checks and `src/robustness.test.ts` for regression coverage on malformed or ambiguous inputs. Benchmarks live in `bench/parse.bench.ts`. `dist/` is generated by `tsup`; do not edit it manually.

## Build, Test, and Development Commands

- `pnpm build` builds the package into `dist/`.
- `pnpm test` runs the Vitest suite once.
- `pnpm test:watch` runs tests in watch mode during development.
- `pnpm bench` runs Vitest benchmarks for parser throughput.
- `pnpm lint` and `pnpm lint:fix` enforce ESLint rules.
- `pnpm format` and `pnpm format:check` apply or verify Prettier formatting.
- `pnpm typecheck` runs `tsc --noEmit`.
- `pnpm release:check` runs the full prepublish gate, including `npm pack --dry-run`.

## Coding Style & Naming Conventions

This repo uses TypeScript with ESM, Node 20+, 2-space indentation, semicolons, double quotes, trailing commas where valid in ES5, and a 100-character print width. Follow the existing module naming pattern: short, lowercase, hyphen-free filenames in `src/`.

Prefer `import type` where possible; ESLint enforces this. Prefix intentionally unused variables with `_`. Avoid `console` in library code unless the warning is justified.

## Testing Guidelines

Vitest is the test runner, and `fast-check` is used for fuzz/property coverage. Add focused unit tests for every parser rule or helper change, especially around ambiguity, timezone handling, and typo normalization. Name tests after the behavior they guarantee, and keep them beside the implementation. There is no explicit coverage threshold, so rely on regression tests for each new phrase pattern.

## Commit & Pull Request Guidelines

Match the existing Conventional Commit style: `feat: ...`, `chore: ...`, and release commits like `chore: release 0.1.2`. Keep commits scoped to one behavior change.

Pull requests should describe the affected Spanish expressions or scheduling rules, list the commands run locally, and note any API or result-shape changes. If parsing behavior changes, include a few representative input/output examples and update `README.md` when the public API or documented coverage changes.
